# Как я использую Claude Code

Это мой персональный сетап Claude Code и короткий гайд, как я с ним работаю. Всё, что нужно скопировать к себе — лежит в папке [home-claude/](home-claude/). Инструкция по установке — [INSTALL.md](INSTALL.md).

Гайд построен как «сверху вниз»: сначала базовые вещи, которые полезны всегда, потом тонкости, которые выстрелят через пару недель работы.

## Универсальный workflow для агентных LLM

Новый setup не привязан к каталогу конкретного инструмента: общие правила,
память, sessions и portable skills хранятся в `.agents/`. Гарантированные
адаптеры для Claude Code и Codex создают только нативные entrypoints и
wrapper'ы, а затем ссылаются на это единое ядро.

Начните с [SETUP.md](SETUP.md). Репозиторий используется как одноразовый
bootstrap: после глобальной установки остаются автономный Python-manager и
skill `agent-workflow-setup`, поэтому checkout больше не нужен для настройки
проектов. Старые Claude-only материалы ниже сохранены как исходный
практический гайд и как вход для будущей миграции.

## 1. Глобальный `CLAUDE.md` в `~/.claude/`

Самая первая штука, которую стоит настроить — это глобальный `CLAUDE.md` в домашней директории `~/.claude/`. Эта штука **автоматически подгружается в начало любой сессии Claude Code**, независимо от того, в каком проекте ты запустился.

Туда надо писать **только глобальные вещи**, актуальные всегда и везде. У меня там, например:

- Что это домашний ПК, корпоративного VPN нет, доступа к стендам/Нексусу/Кафке тоже нет — поэтому не надо пытаться ничего запускать или к чему-то подключаться для проектов, которые лежат в `~/sync-projects/`.
- Что у меня есть своя тулза синкалки кода между этим ПК и корп-ноутом, и как Claude должен себя вести в проектах из `sync-projects/` (не коммитить `.claude/`, `CLAUDE.md`, `docs/` — они локальные и корпу не нужны).
- Что хостовая OS — Windows, shell — Git Bash, поэтому не надо сильно упарываться в башизмы.
- Правила вызова сабагентов-ревьюверов (об этом ниже).

Пример моего `CLAUDE.md` лежит в [home-claude/CLAUDE.md.example](home-claude/CLAUDE.md.example) — его надо переделать под свою ситуацию. **Не копируйте как есть** — там прибиты гвоздями мои пути, моя тулза и моя специфика двух тачек.

## 2. Память проекта

У Claude есть **автоматическая память** — он сам пишет туда вещи типа «юзер — data scientist», «юзер просил не мокать БД в тестах», архитектурные заметки, ссылки на дашборды. По дефолту он кладёт её в `~/.claude/projects/<encoded-cwd>/memory/`, где slug — это закодированный абсолютный путь к проекту. **Я этот дефолт отключаю** через настройку `autoMemoryDirectory` (см. ниже) и держу память в **двух явных местах**:

| Где лежит                       | Что там хранится                                                                                              | Как подгружается                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `~/.claude/memory/` (глобально) | `feedback` (коррекции твоего поведения), `user` (роль/предпочтения), кросс-проектный `reference`              | Авто-подгружается в каждую сессию настройкой `"autoMemoryDirectory": "~/.claude/memory"` в `~/.claude/settings.json` |
| `<repo>/.claude/memory/` (per-project) | `project` (архитектура, incidents, почему так сделано) и repo-scoped `reference` (Linear, Grafana, Confluence) | Подгружается директивой в локальном `CLAUDE.md` репо (есть в шаблоне `/init-claude`) |

**Раскладка внутри:**

- Глобальная — **подпапки по типу**: `~/.claude/memory/feedback/<topic>.md`, `user/<topic>.md`, `reference/<topic>.md`. Имена файлов тип не повторяют — подпапка уже его несёт. Плюс файл-индекс `~/.claude/memory/MEMORY.md` со списком записей.
- Проектная — **плоско**: каждый файл по определению проектный, тип лежит в frontmatter (`type: project | reference`). Индекс — `<repo>/.claude/memory/MEMORY.md`.

**Почему я отказался от дефолтного slug-based пути:**

- Slug — это закодированный абсолютный путь. Переименовал/переместил проект — slug сменился, память оторвалась.
- Кросс-проектные insight'ы (например, `feedback` про твою манеру работы или `user` про твою роль) при slug-схеме разбегаются по разным slug-папкам, хотя должны жить в одном месте и подгружаться везде.
- Единый глобальный путь + явный per-project в репо — проще держать в голове и проще объяснять другому человеку.

**Зачем держать project-память прямо в репо**, а не в общем `~/.claude/`:

- **Видна прямо в IDE.** Файлы открываются вместе с кодом, не надо лезть в отдельный путь.
- **Searchable вместе с кодом.** Grep по проекту захватывает `.claude/memory/` автоматически.
- **Едет с проектом.** Перенёс/переименовал репу — память поехала вместе.
- **Слэш-команды и сабагенты этого ожидают.** `/init-claude` создаёт `.claude/memory/`, `code-reviewer` и `plan-reviewer` читают оттуда — workflow уже завязан на project-local расположение.
- **Можно расшарить на команду.** Если команда решит принять Claude как стандарт, путь становится коммитабельным, и накопленный контекст начинает работать на всех. Пока этого нет — у меня папка `.claude/` защищена `.syncprotect` от утечки на корп-сторону, в общий git не уезжает, лежит локально.

`feedback` про меня лично и `user` про мою роль — это в любом случае на глобальном уровне, командная политика на это не влияет.

## 3. Session notes — краткое саммари сессий

Помимо памяти, я попросил Claude **в конце сессии писать session note** в `.claude/sessions/YYYY-MM-DD-<slug>.md`. Там он фиксирует:

- **Summary** — 1-3 предложения о чём вообще была сессия.
- **What changed** — какие файлы трогали и **почему** (что поменяли — видно в git, а вот зачем — нет).
- **Decisions** — архитектурные/дизайнерские решения: что выбрали, какие были альтернативы, почему именно это. **Самая важная секция** — это то, что больше нигде не зафиксировано.
- **Challenges / dead ends** — что не сработало, во что утыкались, какие тупики исследовали. Сэкономит часы в будущем.
- **Observed behavior** — эмпирические наблюдения, если что-то реально запускали и что-то нетривиальное увидели.
- **Open threads** — что осталось недоделанным, вопросы, фолоу-апы.

Эти ноты **позволяют не читать кодовую базу заново каждый раз** — при старте новой сессии Claude (или я сам) могу быстро пробежать по заметкам и понять историю решений.

## 4. Слэш-команды

Команды лежат в `~/.claude/commands/` и доступны во всех проектах. У меня их сейчас два кластера: **рабочий процесс в проекте** (бутстрап/сессии/беклог) и **workitems** (дайджест Jira-тасок и GitLab MR'ов — про эту обвязку отдельный разговор в разделе 6).

### Кластер «рабочий процесс в проекте»

#### `/init-claude` — бутстрап свежего проекта

Когда стартуешь Claude в новом репо, первым делом запускаешь эту команду. Она:

1. Смотрит на `pyproject.toml` / `package.json` / `go.mod` / `Cargo.toml`, вытаскивает имя проекта, рантайм, скрипты, точки входа, env-переменные.
2. Создаёт черновик локального `CLAUDE.md` с разделами Project / Environment constraints / Commands / Architecture / Conventions и секцией `TODO — open architecture areas` (её потом заполняешь с Claude'ом поглубже).
3. Создаёт структуру `.claude/memory/` + `.claude/sessions/` + `settings.json` для этого проекта.
4. Если проект лежит в `sync-projects/` — дополнительно создаёт `.syncprotect` и `.syncignore` (чтобы `.claude/` не утекал на корп-тачку).

Идемпотентна — если что-то уже есть, не перезаписывает.

После `/init-claude` имеет смысл пройтись с Claude по кодовой базе ещё раз и заполнить оставшиеся `TODO` в локальном `CLAUDE.md`.

#### `/wrap` — финализировать сессию

В конце сессии: Claude пишет session note по шаблону из секции 3, при необходимости апдейтит память. Занимает 1-2 минуты, экономит час на следующей сессии.

#### `/backlog` — собрать беклог

Во время работы часто всплывают **не относящиеся к текущей задаче штуки**: нашли баг в другом модуле, решили что-то оставить на потом, разбили большую задачу на подзадачи. Всё это фиксируется в session notes в секции `Open threads` с тегом `[backlog:<категория>]`.

`/backlog` сканирует session notes + проджект-память, выдирает оттуда все backlog-теги, дедуплицирует с уже существующими, ранжирует по приоритету (H/M/L), пишет в `.claude/sessions/_backlog.md` и выводит в чат.

Категории: `bug | cleanup | docs | followup | idea | prompt-tuning`.

Приятная фишка — туда же можно добавлять пункт «протестить таску X на корп-тачке», а потом говорить Claude, что протестили/не протестили, он переносит в Resolved.

#### `/pick <id>` — взять задачу из беклога

Резолвит айди (или фрагмент названия) в конкретный бэклог-итем, подтягивает контекст из source-ноты, и **стартует plan mode с этой задачей**. Удобно для разового запуска: запустил Claude → `/pick cleanup-debug-logs` → дальше планирование.

### Кластер «workitems»

Эти команды показывают тебе текущее состояние твоей работы в Jira/GitLab без переключения в браузер. Они **читают локальные снапшоты** в `~/sync-workitems/` и `<repo>/.sync-workitems/`, которые наполняет расширенная синкалка `code-transfer` (см. раздел 6). Если на корпоративной стороне ни разу не запускался `sync task` / `sync review` / `sync feedback` / `sync daily` — команды просто скажут «нет данных».

Все четыре опираются на shared-rules файл `~/.claude/workitems-rendering.md` — там единый формат вывода, эмодзи, drill-in уровней (Level 1 — заголовки, Level 2 — детали MR/таски, Level 3 — diff / draft replies).

#### `/morning` — утренний бриф по всему

Master-команда. За один вызов показывает дайджест изменений с последнего fetch'а: новые таски, обновления статусов, новые комменты в твоих review'ах и feedback'ах. В конце — строка `Итого: 📋 N tasks · 🔍 M reviews · 💌 K feedback`. Дальше можно назвать конкретный id (`GIGADO-311`, `MR-98`) — Claude дрилл-инит в этот item.

#### `/tasks` — только Jira-таски

То же, что tasks-секция в `/morning`, но без reviews/feedback. Удобно когда нужен только Jira.

#### `/my-reviews [<repo>|all]` — MR'ы где ты reviewer

Без аргумента — берёт репо по `basename(cwd)`. С `all` — все репо где есть данные. Показывает изменения в MR'ах, которые ты должен ревьюить. Дальше можно дрилл-инить: `MR-98` → краткий просмотр, `дифф` → код, `сделай ревью` → Claude разберёт diff и предложит замечания + черновики комментов.

#### `/feedback [<repo>|all]` — MR'ы где ты автор

То же, но для своих собственных MR'ов — то есть feedback, который тебе пришёл от ревьюверов. На уровне Level 2 у комментов появляются маркеры 📥 (входящий — от ревьювера) и 📤 (твой ответ). Команда «подготовь ответы» — Claude по каждому 📥-треду выдаст: интерпретацию замечания, предложенный код-fix в `diff`-блоке и **draft reply на русском** для копипаста в GitLab. Очень экономит время на типовых раундах ревью.

## 5. Двухмашинный workflow: code-transfer

_Эта секция актуальна для тех, у кого сбербук без Claude Code + домашний ПК с Claude. Если у вас одна машина — можно пропустить._

Базовая проблема, которую я закрыл: на сбербуке у меня доступ к командному git, Jira, GitLab, стендам — но Claude Code там запустить нельзя. На домашнем ПК — наоборот, Claude есть, корпоративных доступов нет. Хочется редактировать код на домашнем ПК (под Claude'ом), а коммитить и гонять в CI на сбербуке. Все «штатные» варианты неудобные: личный git-remote ставить муторно, по VPN/ssh нет доступа, ручные tar-архивы через мессенджер — каменный век.

Я написал (вмесье с Claude) маленькую тулзу **`code-transfer`** — HTTP-синкалку между двумя ПК в одной локалке:

- **Сервер** запускается на домашнем ПК, слушает `0.0.0.0:3000`, проекты держит в `~/sync-projects/<name>/`. Авторизация — один общий bearer-токен (генерируется при первом запуске, лежит в `config.json`).
- **CLI** копируется на корп-ноут одним файлом — `sync.js`. Ноль зависимостей: только встроенные модули Node.js, никакого `npm install` на сбербуке.
- Общаются по HTTP — tar.gz архивы туда-сюда.

Базовый цикл:

1. На сбербуке работаешь как обычно. Когда хочется попросить Claude что-то сделать — `sync push <project>`. CLI пакует проект (минус `node_modules`, `.git` и что-то добавочное из `.syncignore`), постит на домашний ПК, тот разворачивает в `~/sync-projects/<project>/`. Сервер запоминает «последнее состояние с корпа» как baseline для будущих сравнений.
2. На домашнем ПК открываешь этот проект, запускаешь Claude, правишь файлы. У Claude всё под рукой: код, локальный `CLAUDE.md`, `.claude/memory/`, session notes.
3. На корпе делаешь `sync pull <project>` — сервер считает diff между baseline и текущим состоянием, отдаёт только изменившиеся файлы, накатывает на твою рабочую копию. Дальше обычный `git add` / `git commit` / `git push`.
4. Конфликты (если ты что-то правил и на корпе, и на доме после последнего push'а) ловятся на следующем `push`'е — через 3-way diff против baseline. Push в этом случае целиком отвергается, конфликты можно посмотреть в браузерном дашборде сервера и разрулить через `sync resolve`.

Что **не** уезжает с корпа на дом и обратно: всё, что прописано в `.syncprotect` (у меня там `.claude/`, `CLAUDE.md`, `docs/`). Это локальная Claude-инфраструктура. Кроме того, есть `.syncignore` (формат как у `.gitignore`) для всего, что просто не хочется гонять — артефакты, кеши, etc.

Полная инструкция (как поднять сервер, как ставить CLI на корп, формат конфигов, dashboard со списком проектов и diff'ами, flow конфликтов) — в репе [RunkerTNF/code-transfer](https://github.com/RunkerTNF/code-transfer).

## 6. Workitems: Jira и GitLab без браузера

Кроме базового push/pull кода, у `code-transfer` есть **расширение** — он умеет дополнительно тянуть с корп-стороны данные из Jira и GitLab и складывать их в локальные снапшоты на домашнем ПК. На этих снапшотах работают workitems-команды из раздела 4 (`/morning`, `/tasks`, `/my-reviews`, `/feedback`).

CLI обзавёлся четырьмя дополнительными сабкомандами:

| Команда         | Что делает                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------- |
| `sync task`     | Тянет твои Jira-таски (где ты assignee, не Done) и складывает в `~/sync-workitems/tasks/` на сервере. |
| `sync review`   | Тянет открытые GitLab MR где ты reviewer; раскладывает по `<repo>/.sync-workitems/reviews/`.          |
| `sync feedback` | Тянет открытые GitLab MR где ты author; раскладывает в `<repo>/.sync-workitems/feedback/`.            |
| `sync daily`    | Запускает все три последовательно — утренний sweep одной командой.                                    |

Связка получается такая: на корпе раз в день (или когда душа просит) делаешь `sync daily` — данные по HTTP уезжают на домашний ПК, превращаются в snapshot-файлы. Потом на домашнем ПК открываешь Claude в любой директории и пишешь `/morning` — получаешь сжатый бриф что нового со вчера. Дрилл-ин через `MR-<id>` или `<JIRA-KEY>` — Claude уже видит весь нужный контекст (комментарии, дифф) без открытия браузера.

Идея — **держать Jira/GitLab вне фокуса**, пока ты не решил с ними поработать. Не нужно открывать Jira с утра, листать письма-нотификации, прыгать между MR'ами. Раз в день видишь бриф, дальше работаешь с тем, что реально требует внимания.

Кому это полезно:

- Если ты, как и я, работаешь со связкой «корп-ноут + домашний ПК с Claude» — workitems-команды тут разворачиваются естественно.
- Если у тебя ДЗО-ноут - можно адаптировать эти команды под синк няпрямую, без использованию `code-transfer`. Настоить это поможет сам Claude.

Подробности (как настроить Jira/GitLab токены в `~/.syncrc`, как формируется снапшот, какие категории изменений считаются) — в репе [RunkerTNF/code-transfer](https://github.com/RunkerTNF/code-transfer).

## 7. Сабагенты-ревьюверы

Это второй слой защиты от собственных косяков. У меня два сабагента в `~/.claude/agents/`:

### `plan-reviewer`

Вызывается **в конце plan mode, перед `ExitPlanMode`**. Читает план, читает проектный `CLAUDE.md`, читает `.claude/memory/`, и проверяет:

- Существуют ли все файлы/функции/флаги, на которые ссылается план (часто план придумывает несуществующие вещи).
- Не нарушает ли план conventions из `CLAUDE.md`.
- Не нарушает ли invariants из проджект-памяти (past incidents, subtle pitfalls).
- Scope discipline — не накручивает ли план лишних абстракций.
- Есть ли секция Verification / How to test.

### `code-reviewer`

Вызывается **в конце реализации, перед тем как Claude скажет "готово"**. Читает снапшот плана (`.claude/sessions/_last_plan.md`), читает `git diff`, проверяет:

- Всё ли из плана реализовано.
- Нет ли в диффе **незапланированных правок** («scope creep»).
- Convention compliance (особенно — нет ли лишних комментариев про WHAT, нет ли TODO/commented-out кода).
- Invariants из памяти.
- Безопасность (секреты, `shell=True`, raw SQL).
- Тесты.

**Правила вызова прописаны в глобальном `CLAUDE.md`** (см. секцию `Default review workflow`) — Claude вызывает их сам без напоминания.

Это даёт дополнительный контроль — даже если ты сам на ревью что-то пропустишь, сабагенты с высокой вероятностью поймают.

## 8. Plan mode — всегда начинай с него

Работу я **почти всегда начинаю в plan mode** (Shift+Tab переключает). Claude сначала разбирает задачу, исследует код, предлагает план — и только потом, после твоего ОК, идёт писать код.

### Дефолтный plan mode vs `/superpowers:writing-plans`

Для **большинства задач хватает дефолтного** plan mode. Он быстрый и дешёвый по токенам.

Для **больших вещей с кучей неизвестных** — например, когда я писал ту самую синкалку между тачками — имеет смысл `superpowers:writing-plans` + `superpowers:executing-plans`. Они гоняют многоступенчатую схему с отдельными под-ревью, валидацией, чекпоинтами. **Оверкил для простых задач** и жжёт токены даже на max x5 подписке.

Правило большого пальца: если задача «добавить флаг / поправить баг / дописать эндпоинт» — обычный plan mode. Если «сделать новую тулзу / переделать подсистему» — superpowers.

## 9. Opus vs Sonnet — и управление контекстом

На max-подписке я сижу на **Opus 4.7**. Раньше на общей учётке за $20 юзал Sonnet — **на Opus там токены улетали за 0 секунд, 0 минут**. В целом Sonnet вполне сносно справляется с большинством задач сильно экономя токены. Если у вас про-подписка, то он мастхев, если не хотите из 5-часового лимите работать всего час.

Важное различие:

- **Opus (max) — контекст 1M токенов.** Заморачиваться с компактом контекста почти не нужно.
- **Sonnet — контекст меньше.** Важно **вручную вызывать `/compact`**, когда контекст перевалил за ~50%. Иначе он начнёт забывать.

Независимо от модели — **в конце сессии полезно посмотреть `/context`**. Он показывает, на что конкретно ушли токены: системный промпт, файлы, вывод команд, tool results. Видно узкие горлышки — например, если `/context` показывает 40% на вывод одной команды, значит в воркфлоу явно где-то криво, можно переделать.

## 10. Философия: меньше читать код, больше читать заметки

Главный смысл всей этой машинерии (память + session notes + беклог) — **чтобы Claude не читал всю кодовую базу каждый раз**. Он:

- Из глобального `CLAUDE.md` знает про окружение.
- Из проектного `CLAUDE.md` знает стек и архитектуру.
- Из `.claude/memory/` знает накопленный опыт по этому проекту (почему так сделали, какие были грабли).
- Из последних session notes видит недавнюю историю.

Когда он садится за задачу, он сразу знает **нужный минимум** и читает только конкретные файлы, которые надо потрогать, а не весь репо. Это в разы экономит токены и делает ответы по делу.

## 11. Тюнинг сетапа — спрашивай Claude напрямую

Если что-то в Claude Code надо настроить — **можно прям у него и спрашивать**. Он сам знает:

- Как написать новую слэш-команду (скажи ему «создай команду `/foo`, которая делает X» — он создаст файл в нужном месте).

- Как поправить `settings.json`.

У меня есть даже скилл `update-config` (из `superpowers`), который делает это в интерактиве.

## 12. Тюнинг пермишенов на доверии

На старте Claude спрашивает разрешение **перед каждым `Bash`-вызовом** и многими другими действиями (запись файлов вне CWD, обращение к MCP-серверу). Это утомляет, но это правильное поведение по дефолту — система пермишенов работает по принципу «explicit allow».

Что с этим делать:

- **Не разрешай всё подряд через `Bash(*)` или `Edit(**)`.** Соблазн большой, но цена ошибки тоже большая — Claude однажды захочет `rm -rf`или`git reset --hard` мимо тебя, и ты этого не увидишь.
- По мере того как **сам начинаешь доверять Claude в конкретных операциях** — постепенно добавляй их в `~/.claude/settings.json` (глобально) или `<repo>/.claude/settings.json` (под проект). Пиши **узкими паттернами** — `Bash(git status:*)`, `Bash(npm run test:*)`, а не широкими.
- У меня глобально только безопасные read-only вещи: `ls`, `git status`, `git diff`, `git log`, `stat`, `date`, `test`. Project-specific (типа `Bash(uv run:*)` для Python с `uv` или `Bash(go test:*)` для Go) — кладу в проектный `.claude/settings.json`.
- **Что не разрешать без раздумий**, даже если Claude часто это делает: всё разрушительное (`rm`, `git reset --hard`, `git push --force`), всё что коммитит / пушит наружу, всё что лезет в shared infra. Эти штуки пусть всегда спрашивают — там цена ошибки слишком высокая.

В `superpowers` плагине **относительно недавно появился скилл `fewer-permission-prompts`** — он сканирует твои недавние транскрипты, находит часто-повторяющиеся read-only Bash и MCP вызовы, и предлагает приоритезированный allow-list. Очень удобно: вместо того чтобы дописывать паттерны руками по одному, раз в неделю-две запускаешь его и добавляешь блок уже-проверенных команд. Запускается из чата как `/fewer-permission-prompts` (если плагин установлен).

И отдельно про `~/.claude/settings.local.json` — это куда Claude **сам** дописывает one-shot разрешения, когда ты на prompt'е жмёшь «Always allow». Это локальный мусорник: его не надо коммитить и не надо редактировать руками. Можно периодически удалять для сброса — Claude нагенерит заново нужное через prompt'ы.

## 13. Периодический self-review сетапа

Раз в какое-то время полезно **заставлять Claude ревьюить, как он сам использует свои инструменты**. Например:

- Дать ему почитать свои же session notes за последнюю неделю и спросить: «насколько эти ноты соответствуют правилам из команды `/wrap`? Не пишется ли туда бесполезная херня?». Он неплохо ловит дрифт.
- Раз в пару недель смотреть `/context` и искать паттерны — может быть, какой-то файл читается каждую сессию, хотя достаточно раз в три сессии. Тогда можно его переоформить в память.

Это дёшево и даёт ощутимый buff к качеству сетапа через пару итераций.

## 14. Плагины / MCP — только на уровне проекта

Важно: **всякие плагины, MCP-серверы и т.п. подключай только на уровне проекта, а не глобально.** Иначе они срут в контекст там, где они не нужны — съедают токены и запутывают Claude.

У меня глобально включены только `context7` (актуальная документация библиотек) и `superpowers` — это настолько общие штуки, что имеет смысл везде. Всё остальное (например, MCP для конкретной БД или API) — строго в проектном `.claude/settings.json`.

## Development

This foundation requires Python 3.11 or newer. Install the editable development
environment with `python -m pip install -e .[dev]`, then run the test suite
with `python -m pytest -v`.

The Markdown files under `templates/core/` are canonical. Wheel copies under
`src/agent_workflow/_bundled/templates/core/` must remain byte-for-byte mirrors;
the test suite rejects drift and verifies the installed, non-editable wheel.

## Workflow CLI

The manager provides `scan --agents`, `plan init`, `plan setup`, `apply`,
`doctor`, and `rollback`. Setup is always previewable, uses no network, refuses
unmanaged native entrypoints, and requires explicit trust before loading
Python from an external adapter. Every apply is journaled and can be rolled
back with its journal path.

Exact Claude Code and Codex output is locked by cross-platform golden tests.
Release-time checks that require a real agent session are documented in
[docs/live-smoke.md](docs/live-smoke.md).
